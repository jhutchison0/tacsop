## 0. Audit posture and assumptions

This is a **prioritization decision**, not an operationalized decision model already in code. There is no YAML config to validate, no `validate_weights()` call to grep for, no value function code to inspect. My job here is to apply the discipline of MAUT to a planning question and report whether the lead's proposed scope survives a structured ranking and a sensitivity check.

Assumptions I am naming up front because they drive every score below:

- **Repo scope.** This audit is for the `utils` template repo. "Effort" is local effort. "Downstream propagation cost" is the cost of pushing the change through 11 dependent repos. The two are deliberately separated — that separation is the whole reason the lead is being conservative.
- **Effort and downstream-cost are minimize criteria.** I score them as benefit (100 = lowest cost, 0 = highest cost) so all weights stay positive. This matches the project's own `MAUTScorer` discipline (monotone-decreasing value function, not a negative weight).
- **Each alternative is scored as proposed in the memo.** For section F, scoring "migrate command X to a skill" means scoring the migration *as the memo recommends* (some are migrate, some are keep). A high utility means "yes, do what the memo says for this command."
- **Linear value functions throughout.** None of the criteria here have known threshold, perceptual, or ideal-range behavior at the granularity I have. If a stakeholder later argues that, e.g., "downstream cost" has a hard ceiling above which any item is disqualified, the right move is to swap that criterion to `step` or `logistic` — flag for re-scoring, not a problem with this pass.
- **0–100 raw scores, then divided by 100 to land in [0, 1].** Utility = Σ wᵢ × (rawᵢ/100). All utilities therefore live in [0, 1] as the additive MAUT formula requires.
- **Cardinal scoring, not just rank.** The lead has cardinal preference intensities here ("CONTEXT.md is the *real* gap" is a strong cardinal claim, not a rank statement). That argues against SMARTER/ROC weighting; direct elicitation is appropriate.

I did **not** run the project's own `sensitivity.one_at_a_time` routine on this — there is no scorer instance for a planning memo. I did a hand-calculated alternative-weight scenario (section 6) that mirrors what OAT would produce for the two highest-leverage weights.

## 9. Findings by severity (audit format)

**Critical (would invalidate the decision):** None. Weights sum to 1.0, all utilities in [0, 1], no negative weights, value functions are linear and monotone in the documented direction. The model is structurally sound.

**Warnings (model is suspect in places):**

- **Linear value functions throughout.** I used linear because no criterion has a known threshold or perceptual shape, but "Downstream propagation cost" could plausibly be `logistic` if you believe there's a hard ceiling above which any item is disqualified (e.g., "if it requires every downstream repo to change config, kill it"). If that's how you think about it, re-score D4 and any future LANGUAGE.md-style item under a `step` or `logistic` function — they will fall further. Flag for re-elicitation.
- **No formal `validate_weights()` call.** Manual cross-check confirmed the sum, but this analysis would benefit from being run through the project's own `MAUTScorer` if it gets repeated. Worth converting to a YAML config + scorer invocation if this prioritization is going to happen quarterly.
