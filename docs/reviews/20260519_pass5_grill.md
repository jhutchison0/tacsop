## Job 1 — Footgun Grill

### F1 (BLOCKER) — §7 step 3: the multi-package alternation syntax is broken bash

The entry tells maintainers to customize the case pattern for repos with multiple packages:

```bash
*/src/(pkg1|pkg2)/*.py)
```

This is not valid POSIX `bash` case syntax. Running it exits with `syntax error near unexpected token '('`. The correct forms are either extglob (`*/src/@(pkg1|pkg2)/*.py` — requires `shopt -s extglob` at the top of the script) or the two-branch idiom:

```bash
*/src/pkg1/*.py|*/src/pkg2/*.py)
```

I ran both forms. The bare `(pkg1|pkg2)` form fails on bash. The `@()` form requires adding `shopt -s extglob` before the `case` block, which the hook script does not currently do. The two-branch pipe idiom works without any flag.

**Cost of the footgun**: a maintainer with two packages follows the instruction, installs the hook, and the hook silently exits on syntax error (the `set -uo pipefail` without `-e` means the script errors out but the PostToolUse handler still sees exit 0 from the shell's perspective). They get **no audit log and no error**. This is the worst failure mode: the hook appears to work but does nothing.

**Fix**: in §7 step 3, replace the alternation snippet with the pipe idiom and note that the hook uses `/bin/bash` (not extglob-capable without `shopt -s extglob`).

### F2 (HIGH) — §7 step 5: "merge into your existing settings.json" is under-specified

The instruction says:

> Merge into your existing settings.json (DO NOT REPLACE the whole file — preserve your existing `env`, `permissions`, etc.)

The provided snippet is a bare `"hooks"` block. A downstream repo that already has a different `PostToolUse` hook (e.g., a linter hook, or a hook from a prior cycle) will destructively overwrite it if they paste naively. The entry gives no example of what a merge looks like when the `"hooks"` key already exists.

The minimum needed is a worked example showing the merge in the case where a prior hook block is present:

```json
// BEFORE (existing)
"hooks": {
  "PostToolUse": [
    { "matcher": "Bash", "hooks": [{ "type": "command", "command": "..." }] }
  ]
}

// AFTER (merged, not replaced)
"hooks": {
  "PostToolUse": [
    { "matcher": "Bash", "hooks": [{ "type": "command", "command": "..." }] },
    { "matcher": "Write|Edit", "hooks": [{ "type": "command", "command": "..." }] }
  ]
}
```

Without this, a maintainer who has no prior hooks pastes correctly; a maintainer with prior hooks faces a JSON structure decision with no guidance. Given that 11 repos are receiving this, at least some of them will have hooks.

### F3 (HIGH) — §8: Silent deletion of a locally-customized skill

The entry says:

> Delete `.claude/skills/session-end.md` if your repo has it.

There is no prior warning that downstream repos may have customized this file. The session-end skill was propagated in an earlier cycle as template-copy. Any repo that edited it locally (added project-specific steps, changed edge types, modified the body template) will silently lose those customizations.

The entry should add a pre-condition: "Before deleting, diff your copy against the utils original to check for local additions. If your copy diverges, extract your additions into `.claude/commands/session-end.md` or into your local `docs/session-doc-format.md` first."

There is no rollback mechanism for this deletion once committed.

### F4 (HIGH) — §5 step 2: Directory replacement has no diff-first warning

The instruction for the three skill refactors says "replace the single file with the directory." It does not tell the maintainer to diff their copy of the single-file skill against the utils original before replacing.

Any downstream repo that customized `.claude/skills/shift-left-testing.md` (added project-specific tiers, changed mock patterns, added domain examples) will lose those customizations. The entry's rollback section says "revert by restoring the prior single-file from git history" — but that requires the maintainer to remember their customizations existed, and to re-apply them to the new directory form. "Restore from git" is not a lossless rollback if the downstream repo never committed the version they actually used.

**Fix**: add to §5 step 2 — "Before deleting the single-file version, run `git diff HEAD:.claude/skills/shift-left-testing.md` against the utils reference file. If your version diverged, carry those changes into the relevant sidecar."

### F5 (MEDIUM) — Substitution surface is larger than the entry says

The entry calls out `myproject` → `yourpkg` in §7 step 3 (hook script) and §10 (CLAUDE.md template). There is a third implicit substitution site: the `python-prototyper.md` agent definition (adopted via §9) contains `src/myproject/` in the Project Layout and Scope sections. A maintainer who copies python-prototyper verbatim without substituting will have an agent that audits the wrong path.

The adoption-mode table entry for #20 says "TEMPLATE-COPY — Universal workflow improvement." It is not fully universal — it has a hard-coded `src/myproject/` reference that must change. Either change #20's mode to CUSTOMIZE, or explicitly note the substitution requirement.

There are at least three substitution sites the entry mentions or implies. A "substitution checklist" at the end of §7 naming all three would prevent the maintainer from missing one.

### F6 (MEDIUM) — §7 step 8 verification instruction is fragile

> Verify by editing any file under your package's `src/`. Check `.claude/audits/shift-left-violations.log` for a fresh entry.

This verification step assumes the audit log file appears at all. If `jq` is not installed (the hook silently exits on missing jq per lines 17–19 of the script), the maintainer edits a file, checks the log, finds nothing, and has no diagnostic path. The entry should add: "If the log is empty, first check that `jq` is available (`which jq`). The hook exits silently without jq."

Also: "open `/hooks` in Claude Code to reload settings, or restart the session" — the `/hooks` command is not documented in CLAUDE.md. A maintainer unfamiliar with this Claude Code-specific mechanism has no way to know it exists. Spell it out: "In Claude Code, run the `/hooks` slash command to reload hook configuration without restarting the session."

### F8 (LOW) — 22 artifacts: realistic adoption fraction

The Adoption-Mode table has 22 rows. Realistic reading: maintainers under time pressure will stop at the first artifact that requires judgment and skip the rest. The most likely systematic skip is artifact #12 (the hook) because it requires the most steps (7), the most judgment (path substitution), and the only real configuration change. The enforcement layer — the most novel artifact in the cycle — is also the one with the highest skip probability.

There is no prioritization signal in the table. A maintainer who can only do 10 of 22 artifacts today has no guidance on which 10 matter most.

The entry has a "Suggested Adoption Order" section that partially addresses this. But the table itself (which is where the eye goes first) has no priority annotation. Consider adding a "Priority" column: CORE / STANDARD / OPTIONAL.

### F9 (LOW) — Cross-section dependency not called out: §10 assumes §7 is done

The CLAUDE.md template in §10 references the hook and its log path. If a downstream maintainer applies §10 but skips §7, their CLAUDE.md will reference a hook that doesn't exist. The hook reference in §10 is not framed as conditional.

## Job 2 — Omissions

### O1 — No guidance on what to DO with MISSING_TEST log accumulation

`ENFORCEMENT.md` says to "convene a review" when violations exceed 20 in a month. The entry does not say this. A downstream maintainer who installs the hook will accumulate `MISSING_TEST` entries and have no signal for what the expected response is. They will either ignore the log or become anxious about it.

The entry should add one sentence at the end of §7: "After a few weeks, review `.claude/audits/shift-left-violations.log`. If MISSING_TEST count exceeds 20, consult `.claude/skills/shift-left-testing/ENFORCEMENT.md` for escalation triggers."

---

### O2 — No hook verification test for repos that already have audits/ entries

§7 step 8 tells the maintainer to edit a file and look for a fresh entry. This works for a fresh repo. For a repo that already has an audits log with many entries (possible in future cycles), "check for a fresh entry" means scrolling to the bottom. A more reliable test: "Confirm by checking the log's last-modified timestamp matches the current time — `ls -l .claude/audits/shift-left-violations.log`."

Minor, but this is the one verification step in the whole entry.

---

### O3 — No conflict-resolution guidance for locally-customized python-prototyper

§9 says "copy verbatim (or merge the workflow inversion + the pillars-reference fix if you've customized the agent locally)." The parenthetical is the entire conflict-resolution guidance. It does not say:

- What to look for in the diff (the workflow block, the Design Principles section, the Scope block).
- What "merge the workflow inversion" looks like when the downstream agent has added project-specific steps.
- What to do if the downstream version has additional Write paths in Scope that the utils template doesn't have.

For an agent definition — which directly shapes code-writing behavior — "merge locally if you've customized" is too thin.

---

### O4 — No pre-flight checklist

The entry has a "Suggested Adoption Order" at the end but no "Pre-flight" section at the top. Downstream maintainers should verify before starting:

- Tests are green on main (so breakage after adoption is attributable).
- No in-progress branch modifying CLAUDE.md or `.claude/settings.json`.
- `jq` is installed (for the hook).
- Python 3.11+ available (for §11).

These are conditions, not steps. Putting them at the top as a 4-item checklist takes 30 seconds and prevents mid-adoption surprises.

---

### O5 — No "Time to Apply" estimates

22 artifacts with no time signal. A per-section estimate (even rough: 5m / 15m / 30m) would let a maintainer triage by available time and know when they are committing to a long session. This is especially useful for the hook section (§7), which is the most time-intensive.

## Job 3 — Bold Alternatives

### B1 — A `scripts/adopt_doctrine.py` helper for the mechanical parts

**What changes**: Add to the propagation cycle a companion script (or expand `propagate_doctrine.py`) that, when run in a downstream repo, automates the mechanical steps: copy files from utils, perform path substitution (prompting for package name once), append `.gitignore` lines, and report what requires manual attention. The script does not apply "CUSTOMIZE" artifacts; it only handles "TEMPLATE-COPY" ones.

**Why**: The 22-artifact entry has roughly 15 template-copy artifacts. Running 15 copy operations manually is where errors accumulate. A script that does the copies and substitutions and prints "these 7 require your judgment" reduces the error surface to where human judgment is actually required.

**Cost**: Author-side — 1–2 sessions to write and test the script. Reviewer-side — the script itself becomes a propagation artifact requiring its own review gate. Risk: if the script has a bug, it applies that bug to 11 repos simultaneously. Mitigation: dry-run mode and a confirmation prompt before writing.

This is a separate-cycle artifact — do not ship it in this cycle (see Anti-recommendations).

---

### B2 — Per-section "Time to Apply" + Priority annotation in the Adoption-Mode table

**What changes**: Add two columns to the Adoption-Mode table: `Priority` (CORE / STANDARD / OPTIONAL) and `Est.` (rough time). Example:

| # | Artifact | Mode | Priority | Est. | Notes |
|---|---|---|---|---|---|
| 12 | Hook script | CUSTOMIZE | CORE | 15m | Most novel; do not skip |
| 13 | settings.json merge | TEMPLATE-COPY | CORE | 5m | Merge, not replace |
| 19 | Python 3.11 bump | TEMPLATE-COPY | STANDARD | 5m | Verify env first |
| 18 | Propagation protocol | SKIP-OR-CUSTOMIZE | OPTIONAL | — | Hub repos only |

**Why**: Without priority signal, a time-pressed maintainer skips arbitrarily. With CORE / STANDARD / OPTIONAL, they can rationally defer OPTIONAL items and still get the load-bearing changes in.

**Cost**: Author-side — 30 minutes to annotate all 22 rows. Reviewer-side — must validate that CORE/STANDARD/OPTIONAL designations are defensible. Low risk.

---

### B3 — Make §7's verification step a shell one-liner

**What changes**: Replace the prose verification instruction in §7 step 8 with a copy-paste shell command:

```bash
touch /tmp/verify_hook_test.py  # not a real file; triggers the name-match check
# Instead: edit any real src file and check:
echo "# test" >> src/<yourpkg>/utils/__init__.py && \
  sleep 2 && \
  tail -1 .claude/audits/shift-left-violations.log
```

More practically: provide a self-contained verification command the maintainer can run from the repo root to confirm the hook fires, rather than requiring them to perform an actual edit.

**Why**: The current verification step requires the maintainer to understand the hook mechanism enough to know what "a fresh entry" looks like, what file to edit, and where to look. A shell one-liner is unambiguous and reproducible.

**Cost**: Author-side — 10 minutes. Reviewer-side — must verify the command works as described. The command touches production source code slightly (the `# test` comment), which is a minor cost; a test file path would be cleaner but won't trigger the hook.

## Anti-Recommendations

**Do not add a "Why we made these changes" narrative section.** That story is already in `docs/sessions/20260519_doctrine_artifact_buildout.md` and the Pass 4 reviews. Duplicating it in the entry inflates a long document and will drift.

**Do not ship the adoption helper script (`B1`) in this cycle.** Adding a 22-artifact bundle plus a new propagation script in the same cycle doubles the review surface and introduces a bug vector that acts on 11 repos simultaneously. Keep cycle scope tight; propose the script for the next cycle after this one has been consumed.

**Do not try to make the entry self-sufficient.** Several instructions already link out to `ENFORCEMENT.md` and `VERTICAL-SLICING.md`. That is correct. Do not duplicate enforcement rationale or TDD discipline into the entry itself — the links are the contract; the sidecar files are the substance.

**Do not add a per-developer opt-out workflow to the entry.** The entry already covers this in §7 step 9 ("per-developer override: `settings.local.json`"). Adding more override guidance would signal that bypassing the enforcement layer is routine behavior, which undercuts the whole cycle's purpose.

**Do not change the ENFORCEMENT.md escalation threshold** (20 MISSING_TEST / month) in this entry. That threshold was MAUT-derived. If downstream feedback suggests it's wrong, it gets revisited via a new MAUT — not adjusted inline in a propagation entry.
