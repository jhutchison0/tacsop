## Cross-cutting findings (read these first; they constrain every recommendation below)

### F1. The plan contradicts itself on commands vs skills

The plan asserts in section F a clean rule ("commands are for user-controlled timing, skills are for Claude-decided timing") and uses that rule to migrate `session-end` and `pcc` to skills. But the same section then says:

> Keep a `/session-end` slash trigger via skill frontmatter; Anthropic now supports explicit invocation of skills with `/name`.

And earlier in section A #2 (verbatim Anthropic quote it cites):

> "A file at `.claude/commands/deploy.md` and a skill at `.claude/skills/deploy/SKILL.md` both create `/deploy` and work the same way."

If commands and skills are the same surface with two invocation modes, then **the migration is a no-op from the user's perspective**. The plan is using "migrate to skill" to mean "add an autonomous-trigger path while keeping the slash command." That is fine as a design idea but it is not a migration; it is an *addition*. The framing in F therefore overstates the change and understates the cost (you still maintain both the command and the skill body). Flag this before you commit to "migrating" anything — the real decision is whether you want Claude to be able to *self-invoke* PCC or session-end, not whether the slash command should exist.

I take this contradiction as an indicator that the plan's authors have not fully reconciled the new unified-primitive model. Bias your decisions toward "keep the command file, optionally also publish a skill that wraps it" rather than "delete the command file."

### F2. The plan asserts CONTEXT.md is "the biggest gap" without checking config/project.yaml

`config/project.yaml` already encodes a structured subset of what a CONTEXT.md would carry:

- `project.name`, `project.description`, `project.python_requires`
- `design_pillars` (named list)
- `paths` (directory taxonomy with stable names — `source`, `tests`, `config`, `docs`, `sessions`, `plans`, `reviews`)
- `build_phases` (phase names and statuses)
- `state.active_work`, `state.known_issues`, `state.last_session`

A CONTEXT.md as Pocock describes it is a **glossary of domain nouns**, not a project-state file. The two are complementary, not duplicative — but the plan describes CONTEXT.md as if no project-level structured doc existed today, which understates how much overlap will exist once you start populating CONTEXT.md with terms. Practical implication for the audit: the unique value of CONTEXT.md is *domain vocabulary* (e.g., for the decision-science module: `MAUT`, `value function`, `SMARTER`, `weight elicitation`, `dominance`, `tornado plot`). It is **not** project metadata (paths, phases). Scope the new artifact accordingly so it does not drift into duplicating project.yaml.

### F3. Downstream propagation cost is invisible in the plan

The plan never engages with the propagation mechanism. Every recommendation in sections D, E, and F would flow through `scripts/propagate_doctrine.py` -> `.claude/upstream-update.md` -> up to 11 downstream repos. That mechanism currently writes **one notification per latest entry** (see `propagate_doctrine.py:47-66`, `extract_latest_entry` returns only `entries[0]`). Each doctrine update needs to be:

1. Small enough to fit one entry under `docs/doctrine-updates.md` `##` heading
2. Bounded in scope so downstream maintainers can apply it in one session
3. Backwards-compatible by default (the existing entries in `doctrine-updates.md` all use additive language: "if your repo does X, do Y; otherwise no action")

Several plan recommendations (especially #7 `session-end` migration, #8 `pcc` migration, and #4 adding a 4th pillar) violate at least one of these properties. Specifics in the per-recommendation deep-dives below.

### Rec 3 — Upgrade `shift-left-testing.md` to enforce vertical-slice TDD (D.P1 #3)

**Verdict: ADOPT-WITH-MODS**

**Integration consistency.** Fits cleanly with the existing pillar. The current `.claude/skills/shift-left-testing.md` (30 KB) is heavy on test infrastructure (pyramid, mocks, CI) and light on **agent discipline** during a session. Adding the Pocock planning checklist and the explicit "one test, one impl, never bulk-RED" rule is a genuine upgrade — and it is the upgrade that closes the most common failure mode I see in code review (agents writing all tests at once, then all code at once, then declaring victory).

**Concrete artifact impact.**

  - The rule "tests verify behavior through public interfaces, not implementation details"

Rewrite step 3-5 of the workflow to enforce one-test-one-impl loops. This is the lowest-risk place to encode the discipline because python-prototyper is the only Write agent.
- Edit: `.claude/agents/test-runner.md` — add a note that test-runner can be invoked **between** RED and GREEN to confirm the test fails for the right reason. **Hidden coupling.** `bug-fix.md` already enforces RED-first via the regression test loop (see steps 3-4). Make sure the upgraded `shift-left-testing.md` does not contradict it — they should reinforce each other.

### Rec 10 — `interface-designer` agent with 3+ parallel subagents (E #1)

**Verdict: DEFER (pilot first)**

**Integration consistency.** Conceptually clean — it would feed the existing `proposer -> code-reviewer` debate. But it changes the agent model in three ways the plan elides:

1. New agent type (parallel-subagent dispatcher). The current agent fleet is all single-context.

**Concrete artifact impact if adopted.**

**Downstream propagation cost.** Medium-high. Adding an agent is propagable but adoption is friction — most downstreams won't actually use a parallel-subagent agent unless their work routinely involves novel interface design.

**Naming collisions.** None.

**Hidden coupling.** The plan's H #5 acknowledges no head-to-head data exists between sequential debate (your current pattern) and parallel exploration (`design-an-interface`). That uncertainty should be resolved with a pilot in utils before propagating to 11 repos.

**Mods.** Run a one-feature pilot inside utils.
